Cài đặt & thử nghiệm thành công

Redpanda

  • Cài từ repo linux.pkg.redpanda.com, bootstrap một node với IP VM.
  • Service redpanda chạy ổn định; chạy lại script cài đặt không lỗi.
  • Giới hạn RAM Redpanda ~2G trên VM 4GB — phù hợp lab.

Topic (tạo bằng rpk trên VM)

TopicPartitionReplicationRetentionNén

Producer & listen (không mất message)

  • Producer: python producer.py --count N — topic mblife.pbx.cdr.v1, key = linkedid, acks=all, idempotence, nén zstd.
  • Consumer: python consumer.py — group cdr-backend-writer, commit thủ công sau khi ghi DB.
  • Nghe trực tiếp trên broker: rpk topic consume mblife.pbx.cdr.v1 -n 5 — xác nhận message đã vào topic.
  • Đối chiếu: check.py so high-watermark từng partition với COUNT(*) trong cdr.db.

Đã chứng minh: tạo topic → gửi → consume/listen → commit offset → replay an toàn (idempotent upsert theo linkedid).

Hiểu về Kafka: Producer → Broker → Consumer

Trong lab, Redpanda đóng vai Kafka Broker: lưu log theo topic/partition, phục vụ API tương thích Kafka (cổng 9092). Ứng dụng Python dùng confluent-kafka như với cluster Kafka thật.

consumer.py
  • Producer gửi bản ghi (value JSON CDR) kèm key (linkedid). Broker chọn partition = hash(key) % số_partition (cùng key → cùng partition, thứ tự offset trong partition được bảo toàn).
  • Broker (Redpanda) append message vào log partition; replication/retention/compression cấu hình ở topic.
  • Consumer thuộc consumer group: mỗi partition chỉ được một member trong group đọc tại một thời điểm; commit offset sau khi ghi DB thành công.

Lab CDR: Asterisk (tương lai) hoặc script giả → Producer → mblife.pbx.cdr.v1 → Consumer → SQLite. Redpanda là “sổ cái” trung gian chịu tải khi backend chậm hoặc tắt.

Chọn Key để phân bố partition hợp lý

Partition quyết định song song mức nào: nhiều partition + nhiều consumer → xử lý parallel. Key điều khiển message nào đi cùng một “băng chuyền”.

Ví dụ: không nên dùng mã_khách_hàng_doanh_nghiệp làm Key

Key = mã doanh nghiệp

100 doanh nghiệp, một tập đoàn chiếm 80% lưu lượng cuộc gọi. Cùng một mã khách hàng → hàm băm đẩy toàn bộ 80% vào đúng một partition.

Consumer gán partition đó chạy CPU 100%; các consumer ở partition còn lại gần như idle — hot partition, lãng phí cluster.

Hướng chọn key tốt hơn
  • linkedid (lab hiện tại): mỗi cuộc gọi một key — phân tán đều hơn giữa 6 partition; vẫn giữ thứ tự event cùng cuộc gọi nếu mọi event dùng cùng linkedid.
  • uniqueid / call-id ngẫu nhiên khi chỉ cần throughput, không cần gom theo tenant.
  • Key tổ hợp đã băm (ví dụ tenant_id + shard) nếu cần vừa gom nhóm nhỏ vừa tránh một tenant khổng lồ.
  • Không key (round-robin): tối đa cân bằng partition, mất đảm bảo thứ tự theo thực thể nghiệp vụ.

Trong producer.py, key = linkedid (RUN_ID.micro_index) là lựa chọn phù hợp cho CDR từng cuộc gọi, không gom theo doanh nghiệp — khớp kết quả lab (500 message rải watermark trên cả 6 partition).

Offset — “kẹp đánh dấu trang” của Consumer

Mỗi partition là một “cuốn sách” message được đánh số 0, 1, 2, … Offset là số trang Consumer vừa đọc (hoặc vừa xử lý xong và commit).

Commit offset trước khi ghi DB xong → có thể mất message khi crash. Lab commit sau DB → an toàn hơn; replay + upsert xử lý trường hợp đọc lại.

Tóm tắt

  1. Redpanda trên VM lab healthy; topic CDR/insight tạo thành công; dev machine kết nối :9092 OK.
  2. Producer gửi, rpk topic consume và consumer.py listen/ghi DB thành công; tổng 805 message đối chiếu OK.
  3. Mô hình: Producer → Redpanda (broker) → Consumer group + offset commit.
  4. Key quyết định cân bằng partition — tránh key theo doanh nghiệp lớn; lab dùng linkedid per cuộc gọi.
  5. Offset là bookmark của consumer trên từng partition — nền tảng cho backlog, replay và kiểm tra check.py.
