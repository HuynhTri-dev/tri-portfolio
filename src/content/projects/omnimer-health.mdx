## Problem Statement & Scope

Existing digital health solutions currently face three significant market gaps:

- **Passive Traditional Health Apps:**  
  Platforms like MyFitnessPal primarily focus on logging and displaying static metrics (calories, heart rate, workouts). The data remains fragmented, lacks deep clinical analysis, and rarely translates into actionable daily habits. According to a user survey conducted via Google Forms, **61.5% of users stopped using or uninstalled their health apps** because they failed to provide enough continuous value to sustain long-term engagement.

- **Generic AI Models Lack Personalization and Safety:**  
  Generative AI tools like ChatGPT can answer questions quickly, but rely heavily on manual user prompts. Lacking longitudinal health profiles, historical activity baselines, and clinical safeguards, their advice is often generic or potentially unsafe for medical edge cases.

- **High Cost of Human Expert Consultation:**  
  Medical professionals and personal trainers offer deep, tailored guidance, but their services are expensive and cannot provide 24/7 continuous monitoring.

**OmniMer Health** bridges these gaps by delivering an **AI-driven Digital Health Coach**. It fuses real-time wearable biometric streaming with **Agentic AI** to proactively assist users with nutrition, workout planning, and daily lifestyle habits.

> **My Role:** As the sole **Full Stack AI & Mobile Engineer**, I owned the end-to-end product development—ranging from user need validation via Google Forms, microservices backend architecture, and AI reasoning pipelines, to the Flutter mobile client implementation.

OmniMer Health is engineered around three strategic pillars:

1. **Vital Rules Engine (VRE) – Real-Time Sensing Layer:**  
   Ingests and processes continuous biometric streams (Heart Rate, SpO2, HRV) from wearables to compute adaptive personal baselines and detect anomalies in real time.

2. **Expert Think Agent – Analytical Reasoning Brain:**  
   Orchestrates complex multi-step reasoning using a 3-tier memory model (Short-Term, Long-Term, Context Window) combined with **Hybrid RAG** (Qdrant Vector DB + Neo4j Knowledge Graph).

3. **Personalized Safety Guard (PSG) – Safety & Compliance Layer:**  
   Enforces strict medical guardrails to ensure all recommendations support everyday wellness without replacing professional medical diagnosis.

## Vital Rules Engine (VRE) – Real-Time Sensing Layer

The VRE operates on a dual-path architecture to achieve immediate emergency alerting while maintaining long-term baseline precision:

### Fast Path (Node.js & BullMQ)
- **Ingestion:** A Node.js API accepts biometric events from mobile clients, enqueuing them into Redis BullMQ (`VitalQueueService.ts`) with exponential backoff retries, instantly returning `202 Accepted` to prevent I/O blocking.
- **Static Threshold Evaluation:** During onboarding before personalized baselines are calibrated, static clinical thresholds protect life safety (e.g., critical alerts when resting heart rate is below 40 bpm or above 150 bpm, or SpO2 drops below 90%).

### Deep Analytics Pipeline (Kafka Stream & Python Worker)
Kafka messages (`topic.vital.stream`) are consumed by a Python worker (`vital_rules_worker.py`) across a 5-stage pipeline:
1. **Noise Filtering:** Discards physically invalid readings (e.g., Heart Rate outside 30-220 bpm) and removes transient spikes (spike detection triggers if readings shift >50% within 60s).
2. **Adaptive Z-Score Evaluation:**  
   Computes standard deviation offset from the user's baseline:
   ```text
   Z = (x - μ) / max(σ, 0.01)
   ```
   Risk categorization: **Critical** (`|Z| ≥ 3.0`), **Warning** (`2.0 ≤ |Z| < 3.0`), and **Normal** (`|Z| < 2.0`).
3. **Action Dispatching:** Manages notification deduplication via Redis time-bucket locks before dispatching APNs push notifications.
4. **Online Baseline Updates (Incremental Welford's Algorithm):**  
   Updates rolling baseline statistics directly on Redis in `O(1)` time without storing full raw event histories:
   ```text
   μ_new = μ_old + Δ / n_new
   M_(2,new) = M_(2,old) + Δ · (x - μ_new)
   ```
5. **Short-Term Memory (STM) Synchronization:** Aggregates daily health flags into Redis buffers for zero-latency LLM context retrieval.

### Calibration & Adaptive Feedback Loop
- **Nightly Population Baseline Sync:** Celery Beat jobs compute 7-day historical population statistics (`N`) from MongoDB at 00:00 UTC, synchronizing baseline parameters back to Redis.
- **Adaptive Threshold Adjustment:** Incorporates user feedback (`False Alarm`, `Acknowledged`, `Escalated911`) to dynamically tune individual sensitivity multipliers (`sigmaMultiplier`), reducing false positive alerts over time.

### StateGraph & Reflexion Loop (LangGraph)
The agent operates as a multi-step reasoning graph built with LangGraph:
- **Context Assembly:** Combines real-time STM states, LTM profiles (medical history and dietary preferences in Qdrant), and graph context from Neo4j.
- **Longitudinal Health Analysis:** Analyzes temporal trends. Critical anomalies immediately route execution to Human-in-the-Loop (HITL) checkpoints.
- **Multi-turn ReAct & Tool Execution:** Leverages domain tools (`calculate_bmr_tool`, `calculate_ncs_tool`, `query_recent_workout_summary`).
- **Reflexion Pipeline:** Evaluates draft outputs (`reflection_evaluation_node`). Safety violations or allergen conflicts trigger a **CRITICAL** flag, invoking self-refinement (`self_refine`) or emergency circuit breaking (`circuit_breaker`).

### Coaching Frameworks (FITT & Nutrition)
- **FITT Framework (Workout):** Pre-fills **F**requency, **I**ntensity, **T**ime, and **T**ype workout dimensions tailored to user activity levels (Sedentary, LightlyActive, VeryActive).
- **Nutrition Framework:** Computes clinical energy needs (BMR/NCS) and target macronutrient distribution ratios:
  - *Weight Loss (Cut):* 40% Protein - 30% Carb - 30% Fat.
  - *Muscle Gain (Bulk):* 30% Protein - 50% Carb - 20% Fat.
  - *Maintenance (Default):* 30% Protein - 40% Carb - 30% Fat.

### Hybrid RAG & Weighted Reciprocal Rank Fusion (WRRF)
Instead of relying on heavy, slow Cross-Encoder rerankers, OmniMer Health fuses **Qdrant Vector DB** (BGE-M3 Dense + BM25 Sparse) with **Neo4j Knowledge Graph** traversals via **Weighted Reciprocal Rank Fusion (WRRF)**:

```text
WRRF_Score(d) = Σ [ w_s / (k + rank_s(d)) ]  where s ∈ {dense, sparse, alias}
```

- **Smoothing Constant:** `k = 60`.
- **Weights:** `w_dense = 1.0`, `w_sparse = 1.0`, and a boosted **`w_alias = 2.5`** to guarantee exact entity matches rank at the top.
- **Canonical Grouping & Query Facet Mapping:** Consolidates entity chunks into unified resource representations while filtering context by intent facets (`mistakes`, `safety`, `steps`, `nutrients`).

### RAG Retrieval & Reasoning Quality (RAGAS Framework)
Evaluated against a curated benchmark of 100 medical health questions with verified ground truths:

- **Context Precision (0.69):** Significantly improved from the **0.42** baseline, proving that Hybrid RAG retrieves exact context while eliminating irrelevant noise.
- **Context Recall (0.66):** Ensures comprehensive retrieval of medical guidelines and user background.
- **Faithfulness (0.78):** Demonstrates strict alignment with retrieved evidence, eliminating hallucinations.
- **Answer Relevancy (0.85):** Highlights sharp focus on user queries driven by tool execution and self-reflection loops.

### Safety Evaluation & Medical Guardrails
Tested against 20 high-risk clinical scenarios:

- **Baseline LLM:** Achieved only **~5% safety recall**, frequently generating dangerous advice during acute medical symptoms.
- **Optimized CoT:** Reached **100% safety recall** but proved over-conservative, rejecting benign lifestyle questions and hurting user experience.
- **OmniMer Health:** Achieved **~90% Safety Recall**, striking an optimal balance between **medical safety** and **interactive user utility**.
